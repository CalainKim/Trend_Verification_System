# 논문과 배포

2026-11-03 논의 기록이다. 결론과 그 근거를 남긴다.

배경은 이렇다. 10주차에 처음으로 유의한 채점 결과가 나왔고, 그 시점에
대회 출품을 목표로 범위를 넓히기로 했다. 앱과 웹, 논문, 외부 공개 배포
셋이다.

---

## 1. 논문 거리

새로운 것과 잘한 것을 갈라서 적는다. 섞으면 심사에서 깨진다.

### 1순위. 근거를 어떻게 적느냐가 판정기의 기권율을 좌우한다

같은 61건, 같은 정답, 같은 숫자를 주고 근거 문장의 단어 하나만 바꿨다.

```
전   "10-09 결측, 10-10 결측, 10-11 결측, 10-12 결측"
후   "10-09 TOP100 밖, ... 여기 적힌 날은 모두 수집이 있었던 날이므로
      'TOP100 밖' 은 자료가 없다는 뜻이 아니라 그날 상위 100위 안에
      없었다는 뜻이다"
```

| | 답한 건수 | 커버리지 | 정확도 | 답한 부분 기저율 | 대비 |
| --- | --- | --- | --- | --- | --- |
| 4차 | 24 | 39.3% | 70.8% | 58.3% | +12.5%p |
| 5차 | 42 | 68.9% | 69.0% | 50.0% | +19.0%p |

데이터는 한 바이트도 바뀌지 않았다. 모델도 설정도 같다.

논문이 되는 이유는 셋이다.

- 측정이 깨끗하다. 바꾼 것이 단어 하나뿐이라 A/B 가 성립한다
- 반직관적이다. 자료를 더 준 것이 아니라 가진 것을 뭐라 부르는지를 고쳤다
- 흔한 함정이다. 결측 처리는 어느 파이프라인에나 있다

그리고 왜 그 단어가 틀렸는지가 구조적이다. 창을 수집된 날로만 만들기
때문에 창 안의 빈칸은 논리적으로 결측일 수가 없다. 코드는 맞았고 설명만
틀렸으며 테스트도 잡지 못한다. 모델만 알아챘고 기권이라는 형태로 알려
주었다.

제목 후보. 근거 서술의 모호성이 LLM 판정기의 기권을 유발한다

### 2순위. 셋을 묶으면 방법론 논문

따로 내기엔 약하고 묶으면 "LLM 판정기를 어떻게 개발하고 평가하는가" 가
된다. 1순위 논문의 방법 절로 넣어도 된다.

**(1) 정답을 사람이 안 정하는 벤치마크**

트렌드 검증의 병목은 정답이다. 진짜 유행인지는 사람이 합의해야 하고 그
합의가 3주 동안 되지 않았다. 질문을 바꿔 피했다. 원인 대신 수명을 묻는다.
사례가 1건에서 620건이 되었다.

**(2) 기권을 진단 신호로 쓴다**

2차에서 전부 기권이 나왔다. 실패로 보이지만 가장 쓸모 있는 실행이었다.

```
2차 기권 사유    계절성 10, 광고와 노출 7, 일별 추이 2
                →  3차에 일별 추이, 4차에 계절성을 넣음
4차 기권 사유    광고 36, 결측 28, 브랜드 13, 할인 10, 계절 6
                →  5차에 결측을 고침
```

기권 사유를 세서 작업 순서를 정하는 루프다. 세 번 돌려 세 번 다 올랐다.
사람이 무엇이 부족할지 추측하는 대신 모델이 지목하게 하는 것이고, 그쪽이
더 정확했다.

**(3) 답한 부분의 기저율로 채점한다**

기권하는 판정기는 쉬운 문제만 골라 답할 수 있다. 전체 기저율과 비교하면
그 선택 효과가 성능으로 둔갑한다.

```
          전체 기저율   답한 부분 기저율
4차         54.1%        58.3%     어려운 쪽을 피했다
5차         54.1%        50.0%     어려운 쪽까지 답했다
```

5차는 정확도가 1.8%p 내려갔는데 성적은 올라갔다. 전체 기저율로 쟀으면
반대 결론이 나온다.

### 재료는 되지만 기여로 내세우면 안 되는 것

- 누수를 함수 분리로 막기. 좋은 엔지니어링이지 새로운 것은 아니다
- 정답 봉인과 해시. held-out test set 의 변형이다
- 기각된 가설 셋. 있어야 할 태도이고 그 자체가 기여는 아니다
- 규칙 기준선 49.2%. 기준선은 당연히 있어야 한다

마지막은 각주로는 쓸 만하다. 사람이 손으로 짠 규칙이 찍기보다 4.9%p
못했다는 사실이, 모델의 우위가 규칙으로도 되는 수준이 아니라는 근거가
된다.

### 지금 모자란 것

- 독립 표본. 61건이 겹친 창 하나에서 나왔다. 신뢰구간이 독립 가정을
  어긴다. 수집이 쌓여야 한다. 가장 큰 구멍이다
- 재현. 1순위 발견이 한 번 돌린 결과다. 같은 조건에서 여러 번 돌려
  기권율이 안정적으로 갈리는지 봐야 한다
- 다른 모델. opus 하나로만 봤다. 다른 모델에서도 같은 일이 나야 모델
  특성이 아니라 서술 문제라고 말할 수 있다
- 선행 연구. 확인하지 않았다. 기권(selective prediction), 커버리지 대비
  정확도, LLM 판정기 평가는 모두 연구가 있는 분야다. 선행을 보기 전에는
  새롭다고 말할 수 없다

재현과 다른 모델 둘은 수집을 기다리지 않고 지금 할 수 있다.

## 2. 배포

### 결론. 웹이다

TestFlight 가 안 되는 이유는 복잡해서가 아니라 외부 테스터가 애플 심사를
거쳐야 하기 때문이다.

```
내부 테스터   심사 없음, 최대 100명, 전부 팀 멤버로 초대해야 함
외부 테스터   베타 심사 필요, 빌드마다, 반려 가능
빌드 수명     90일이면 만료
설치 과정     애플 ID → TestFlight 앱 설치 → 초대 수락 → 앱 설치
```

목표가 "궁금한 사람이 들어와서 확인" 인데 네 단계를 거치게 하면 아무도
보지 않는다. 웹은 링크를 누르면 끝이다.

### 이미 와 있는 것

산출물이 HTML 파일 하나(4.5MB)라 그대로 웹사이트다. 서버도 빌드도 필요
없다. GitHub Pages 가 1순위다. 저장소가 이미 깃허브에 있어 주소와 자동
배포가 따라온다. 현재 Pages 설정은 되어 있지 않다.

### 공개 전에 막아야 하는 것

지금 파일은 심층 검증 버튼을 누르면 보는 사람에게 API 키를 묻는다.

```
내 키를 심어서 올린다    아무나 눌러 돈을 쓸 수 있다. 안 된다
보는 사람 키를 받는다    아무도 쓰지 않는다
```

공개판은 미리 돌려 둔 결과를 보여주는 쪽으로 간다. 61건 판정은 이미 났고
유형 심층 검증도 몇 개 미리 돌려 결과를 박아 두면 된다. 실시간 호출을
넣으려면 작은 중계 서버와 호출 제한이 필요하고, 그것은 나중 문제다.

### 앱

지금 단계에서 네이티브 앱이 더해 주는 것이 없다. 읽는 화면이고 입력도
알림도 카메라도 쓰지 않는다. 같은 웹을 폰 크기에 맞추는 쪽을 택한다. 홈
화면에 추가하면 앱처럼 열리고 앱스토어도 심사도 없다.

대회 요건에 모바일 앱이 명시돼 있다면 판단이 달라진다. 확인이 필요하다.

## 3. 순서

```
1  웹 배포          반나절. 지금 할 수 있다
2  수집 쌓기        기다리면 된다. 독립 창이 늘어야 논문이 선다
3  폰 크기 화면     시안이 나오면
4  논문             2가 어느 정도 차면
```

1이 2보다 먼저인 이유는 수집은 가만 두어도 쌓이지만 배포는 하지 않으면
되지 않기 때문이다. 배포해 두면 미팅에서 링크 하나로 끝난다.
