# Qwen 보류 원인 점검 — 실제 프롬프트와 최종 출력

2026-11-08 · 추가 모델 호출 없음 · 원본 프롬프트·출력·봉인 해시 유지

**예측 지시는 실제로 들어갔다. 그러나 미래 정답이 없는 상태에서 예측하는 과제와, 미래값을 받아 판정식을 확인하는 과제를 충분히 구분하지 못했다.** Qwen의 보류 7건 모두 미래 실측 부재를 주된 이유로 들었고, 유일한 WATCH는 판정 문턱을 미래 평균처럼 사용했다. 우선 과제 전달과 보류 규칙을 점검해야 하는 실행 기록이며, 이 단계에서 모델 성능이나 연구 효과의 결론을 확정하지 않는다.

이번 주 목적은 **연구 환경과 1차 구현·입출력 스펙을 점검·정리하는 것**이다. 정식 연구 질문, 비교 실험, 평가 해석, 논문 방향은 이후 결정한다. 기존 수치와 초안은 재현 가능한 작업 기록으로 남긴다.

## 무엇을 읽었나

- `private/research-pilot/live/frozen.json`에 봉인된 Qwen 8건의 실제 `prompt.system`, `prompt.user`, `prepared_input`, 최종 응답·모델 설정·사용량.
- 각 사례의 Claude 요청과 입력·프롬프트 문자열 및 해시의 일치 여부.
- `src/trend_research/providers.py`, `runner.py`, 저장된 A40 시작 로그와 환경 메타데이터.
- [실제 전송 프롬프트 문자열과 8건 점검 자료](pilot-prompt-v1.json), [최종 출력 공개본](pilot-predictions.json).

프롬프트 JSON은 저장된 실제 문자열의 사본이다. HTTP 패킷 원문을 별도로 캡처했다는 뜻은 아니다. 이 분석은 정답을 대조해 출력의 이유를 역으로 설명하는 방식이 아니라, 모델이 받은 자료와 출력 이유를 대조한다. 내부 추론 전문은 저장하지 않았으므로 모델 내부 원인을 직접 관찰한 것으로 표현하지 않는다.

## 예측 지시는 어디에 있었나

| 위치 | 실제 문구 |
|---|---|
| 시스템 | “WATCH는 상승분 절반 이상 유지의 예측, NOT_SUPPORTED는 그 기준 미달의 예측이다.” |
| 질문 `claim` | “이 상품은 이후 수집이 있는 7개 관측일의 평균 순위에서 감지된 상승분의 절반 이상을 유지하겠는가?” |
| 입력 `limitations[0]` | “확인 구간의 실제 순위는 입력에 없으며, 현재 입력만으로 예측한다.” |

따라서 **‘예측하라는 지시 자체가 없었다’는 진단은 틀리다.** 하지만 다음 문구가 함께 있었고, 보류를 결정하는 경계가 정해지지 않았다.

| 실제 문구·구조 | 점검할 빈틈 |
|---|---|
| “근거가 부족하면 HOLD를 사용” | 부족함이 과거 입력의 결손인지, 미래 정답의 부재인지 구분하지 않았다. |
| “주어진 자료와 정의만 사용”, “미래 관측을 근거로 추가하지 않는다” | 관측 사실을 지어내지 말라는 규칙은 필요하다. 다만 관측이 없는 미래를 추정하는 일은 별도로 허용·요구한다는 설명이 약했다. |
| `base_mean - confirmation_mean >= ...` | 사후 정답 계산식은 있지만, 아직 모르는 미래 평균을 예측해야 한다는 과제 연결이 약했다. |
| “검증 가능한 지지 근거”, “판단에 필요한데 제공되지 않은 정보” | 미래값을 요구하며 검증을 멈추는 답도 출력 형식상 유효해진다. |
| 광고 원인 부재만으로 자동 보류하지 말라는 지시 | 광고 정보에 대해서는 예외를 명시했지만 미래 실측 부재에는 같은 구분을 두지 않았다. |
| 예측 안내 일부가 JSON의 `limitations` 안에 있음 | 시스템은 JSON을 명령이 아닌 자료라고 설명한다. 핵심 과제 지시를 데이터 설명 안에도 넣은 구조가 의도 전달에 도움이 됐는지 확인이 필요하다. |

이 문구들이 논리적으로 반드시 모순되는 것은 아니다. 다만 ‘없는 사실을 만들지 말 것’과 ‘불확실한 미래를 예측할 것’의 역할을 구분하는 설명이 충분하지 않다. 특정 한 문장이 원인이라는 인과 검증은 아직 하지 않았다.

## 8건에서 실제로 무엇을 답했나

상품 번호 앞에는 `rise_2026-10-12_29cm_`가 붙는다.

| 상품 | 판정 | 최종 응답에서 확인한 이유·행동 |
|---|---|---|
| 2816996 | HOLD | “확인 기간 데이터 부재로 판단 불가” |
| 2824007 | HOLD | 과거 상승폭 10계단을 읽었으나 확인 기간 평균·실제 관측이 없다고 보류 |
| 3450561 | HOLD | 과거 평균·상승폭을 적은 뒤 “확인 기간 데이터 부재로 지속성 판단 불가” |
| 4125187 | WATCH | 문턱 95.36을 미래 평균처럼 놓고 판정식에 대입 |
| 4130049 | HOLD | “확인 기간 평균 순위 데이터 누락” |
| 4205647 | HOLD | 미래 평균 부재를 반대 근거에 넣고 “지속성 검증 불가” |
| 4205649 | HOLD | 과거 상승폭 14계단을 읽었으나 확인 구간 부재로 “검증 불가” |
| 4216006 | HOLD | 실제 미래 순위가 없어 평균 순위 계산이 불가능하다고 설명 |

**보류 7건 모두 미래 확인값 부재를 주된 이유로 들었다.** 과거의 변동성·결측 정도를 사례별로 판단해 불확실성이 높다고 설명한 양상과 다르다. 미래 관측을 숨긴 것은 예측 과제의 정상 조건이며 수집 누락 오류가 아니다.

유일한 WATCH의 지지 근거 원문은 다음과 같다.

> 기준 구간 평균 101위, 감지 구간 평균 89.71위로 상승폭 11.29계단. 이후 7개 관측일 평균 95.36위로, 101 - 95.36 = 5.64계단이 기준 상승분 절반(11.29/2=5.645)과 근접하여 지속 기준을 만족.

입력의 95.36은 `confirmation_mean_rank_threshold`라는 **평가 문턱**이었다. 미래 평균의 관측값이나 독립적으로 산출한 예측값이 아니다. 이 값을 미래 평균 자리에 놓은 설명은 예측 근거가 되지 않는다. 또한 표시값 기준으로 `5.64 < 5.645`이므로 가깝다는 이유로 ‘이상’ 조건을 충족한다고 할 수 없다. 이 사례도 사후 판정식의 숫자를 대입하는 방식으로 과제를 처리한 양상이다.

## 환경·전송·후처리 문제인가

| 점검 | 확인 결과 |
|---|---|
| 요청·응답 모델 | 8건 모두 `Qwen/Qwen3-8B` |
| 입력 | 8건 모두 과거 14개 관측과 세 근거 ID 전달. 저장된 user JSON과 prepared_input 일치 |
| Claude와의 입력 동일성 | 사례별 system/user 문자열, input_hash, prompt_hash 모두 일치 |
| 종료 상태 | 8건 모두 `stop`, 출력 543~2,370토큰으로 8,192 상한 미도달 |
| 시간 | 17.45~86.51초로 요청 제한 300초 미도달 |
| thinking | 요청 설정 `enable_thinking=true`, 서버 `qwen3` parser 확인. 실제 내부 추론 내용은 미보관 |
| 후처리 | 응답 JSON과 저장 판정이 8/8 일치. 평가기가 실패를 HOLD로 바꾼 것이 아님 |
| `complete` 상태의 의미 | 형식·인용 ID·종료 상태 검증 통과. 예측 과제를 의미적으로 수행했다는 보증은 아님 |

이 기록에서는 A40 메모리 부족, 잘못된 모델, 잘린 응답, 예외의 HOLD 변환으로 설명할 증거가 없다. 따라서 하드웨어나 출력 제한을 원인으로 잡고 바꾸기보다 과제 지시·보류 규칙을 먼저 점검하는 것이 타당하다.

temperature 0.6은 요청에 명시했고 top_p 0.95·top_k 20은 모델의 generation_config 기본값을 사용했다. 요청 seed는 별도로 지정하지 않았다. 이는 환경 명세에서 구분해 기록할 사항이며, 보류의 원인이라는 증거는 없다.

## 원인 가설과 아직 알 수 없는 것

가장 강한 작업 가설은 **보류 규칙이 열린 상태에서 Qwen이 미래 예측을 사후 확인으로 해석했다**는 것이다. 이 가설은 7건의 보류 이유와 1건의 문턱 대입 양상에 부합한다.

그러나 프롬프트를 달리한 통제 확인을 하지 않았으므로, 특정 문구·한국어 이해·모델별 보수성·특징 표현 방식의 영향을 분리하지 못했다. 프롬프트만 바꾸면 해결된다고 보장할 수도 없다. 동일 프롬프트를 두 모델에 전달한 사실만으로 둘이 동일한 과제를 수행했다고 볼 수 없으며, 현재 수치를 모델의 일반적인 예측 능력 비교로 앞세우지 않는다.

## 1차 스펙에서 정리할 경계 — 아직 적용하지 않은 수정 방향

| 구분 | 명세에 필요한 구분 |
|---|---|
| 과제 | 판단 시점에 서서 과거 흐름으로 미래 지속성을 예상한다. 미래 실측을 받아 정답을 계산하는 과제가 아니다. |
| 미래값 부재 | 의도적으로 가린 정답이므로 부재 자체만으로 HOLD하지 않는다. 미래 관측을 지어내지는 않는다. |
| HOLD | 과거 입력의 어떤 부족함·충돌·불확실성에 허용할지 별도로 정한다. 무조건 이진 답변을 강제하는 방식으로 바꾸지 않는다. |
| 문턱 | 평가 기준과 관측값·예측값을 구분한다. 문턱을 미래 평균으로 대입하지 않는다. |
| 출력 점검 | JSON 유효성과 과제 수행 여부를 분리한다. 미래값을 요구하는 반복 보류와 문턱의 관측값화를 점검 대상으로 삼는다. |

위 내용은 원인 분석에서 나온 수정 지점이며 새 프롬프트나 최종 연구 설계의 확정본이 아니다. 기존 프롬프트·예측·채점 파일은 보존했고 추가 호출하지 않았다. 이번 주 기록은 **환경 연결과 저장·검증 경로를 확인했으며, 예측 지시와 HOLD 정책을 보완할 명세 항목을 찾았다**로 정리한다.
