# 커머스 채널 셋 (2026-11-05)

## 1. 왜 늘렸나

11월 역할 분담에는 "지그재그를 붙인다" 고 적혀 있었다. 2026-11-05 에
robots.txt 를 다시 받아 보니 9월 기록과 달라져서 `User-agent: *` 가
`Disallow: /` 였다. 무신사와 같은 화이트리스트 구조다. 그래서 대체 소스를
여덟 곳 확인하고 둘을 골랐다. 확인 기록은 `robots-compliance.md` 의
"재확인 2026-11-05" 절에 있다.

늘린 이유는 채널 수를 세기 위한 것이 아니다. 지금까지 커머스는 **사실상 한
채널**이었다. 29CM 가 무신사 계열이라 둘을 독립으로 셀 수 없고, 무신사는
robots 가 막아서 애초에 못 모은다. 그러니 "여러 채널이 같은 방향" 이라는
근거를 커머스 안에서는 만들 수 없었다. 코오롱몰과 하이버는 운영사가 달라서
그것이 처음으로 가능해진다.

교란 요인이 서로 다른 것도 중요하다.

    코오롱몰   자사 브랜드가 순위의 절반이다 (측정값 207/400)
               브랜드가 밀어서 오른 것과 사람들이 사서 오른 것이 섞인다
    하이버     편집샵이라 자사 밀어주기가 없다
               대신 할인율이 74~82% 라 재고 소진 압력이 섞인다
    29CM      리뷰 수가 있어서 실제 구매를 거친 증거를 따로 볼 수 있다

세 교란이 같은 방향으로 틀릴 이유가 없다. 그래서 셋이 같은 상품을 가리키면
근거가 세진다. 하나만 가리키면 그 채널의 교란일 수 있다.


## 2. 무엇을 얻고 무엇을 못 얻나

| | 29CM | 코오롱몰 | 하이버 |
|---|---|---|---|
| 채널 | `commerce_rank` | `kolon_rank` | `hiver_rank` |
| 건수 | 카테고리 8개 x 100 | 탭 4개 x 100 | 50 |
| 순위 | 있다 | 있다 | 있다 |
| 순위 점수 | 없다 | 없다 | **있다** |
| 리뷰 수 | **있다** | 없다 | 없다 |
| 좋아요 수 | 있다 | 있다 | 없다 |
| 브랜드 | 있다 | 있다 | 42%만 |
| 의류 카테고리 | **있다 (3단계)** | 없다 | 없다 |
| 자사 브랜드 표시 | 없다 | **있다** | 없다 |
| 계산 시각 | 없다 | 없다 | **있다** |

굵게 표시한 것이 그 채널만 주는 것이다.

### 각 채널의 제약

**29CM** 에만 의류 3단계 분류가 있다. 그래서 상의만 따로 보는 분석은 29CM
에서만 성립한다. 나머지 둘은 상품명으로 유형을 뽑아야 한다.

**코오롱몰** 은 베스트 목록에 카테고리가 없다. `stdCategoryLevel1/2/3` 을
요청은 하지만 응답이 전부 null 로 온다. 카테고리 목록 페이지
(`/Category/List/{코드}`)는 정렬이 `recommendScore-desc` 하나뿐이라 추천
점수지 판매 순위가 아니다. 그래서 순위 자료는 `/Best` 뿐이다.

**하이버** 는 `/ranking` 한 경로뿐이다. `period`, `page`, `limit`, `scope`
를 쿼리로 넘겨도 전부 무시하고 같은 응답이 온다. 그래서 50건이 상한이다.
브랜드가 42% 에만 붙는다. 나머지는 `is_brand_product` 가 false 인 쇼핑몰
상품이라 브랜드명이 빈 문자열로 온다. **빈 값을 상품명 첫 토큰으로 메우지
않는다.** 상품명이 `[노마진] 아미 드 꾀흐 ...` 나 `[당일출고/1+1할인] 남자
코듀로이 ...` 꼴이라 첫 토큰이 홍보 문구이거나 아예 브랜드가 아니다.
추측해서 채우면 틀린 브랜드가 쌓이고 브랜드 겹침 신호가 거짓으로 커진다.


## 3. 기존 분석을 어떻게 안 건드렸나

검증 파트가 지금 자료로 리즈닝 모델을 학습하고 있다. 봉인한 문제지 139건과
기저율 59.7% 가 `commerce_rank` 의 상의 범위로 만들어졌다. 그 범위가 한
행이라도 움직이면 "모델이 기준을 넘었다" 는 결론이 근거를 잃는다. 오류가
나지 않으므로 아무도 모른다.

### 방법은 채널 분리다

새 자료를 `commerce_rank` 에 섞지 않고 별도 채널에 넣었다. `persistence`
의 질의가 전부 `channel = ?` 로 걸리므로 채널이 다르면 기존 질의가
**구조적으로** 안 바뀐다.

카테고리 코드로 거르는 방식(`ANALYSIS_CATEGORY_CODES`)도 있었지만 고르지
않았다. 코드가 우연히 겹치면 조용히 새고, 코오롱몰 코드는 12자리라 29CM
의 9자리와 길이가 달라도 같은 열에 섞이면 구분이 코드 값에만 의존한다.
채널 분리는 그 경로가 없다.

### 증명

손대기 전과 뒤에 분석 범위 시계열의 지문을 떴다.

    항목             손대기 전            코오롱몰과 하이버 수집 뒤
    시계열 키        2,250               2,250
    지문             8d1d95330f035a6a    8d1d95330f035a6a
    관측 일수        39                  39
    기간             2026-09-06 ~ 11-04  2026-09-06 ~ 11-04
    봉인 benchmark   n 139, base 0.402878  n 139, base 0.402878

공개 산출물도 확인했다. `docs/index.html` 과 `docs/cases.html` 에서 코오롱,
하이버, kolonmall, hiver, 그리고 새 채널에만 나오는 브랜드(파타고니아,
헨리코튼, 슈콤마보니)를 찾았고 전부 0건이었다. 바뀐 것은 재고 통계뿐이다
(채널 4개 -> 6개, 레코드 153,955 -> 154,729).

이 경계는 `tests/test_commerce_channels.py` 의 `TestChannelIsolation` 이
지킨다.


## 4. 교차 확인이 실제로 되는지 재 봤다 (2026-11-05 하루치)

채널을 늘린 목적이 "여러 채널이 같은 방향" 이므로, 셋이 같은 것을 가리킬
수 있는지가 먼저 확인돼야 한다. 가리킬 공통 축이 없으면 채널을 늘린 의미가
없다. 하루치로 재 보니 **축에 따라 답이 갈렸다.**

### 브랜드 축은 안 된다

    브랜드 수      29CM 298    코오롱몰 69    하이버 11

    29CM 교집합 코오롱몰      9개   24/7시리즈, 버켄스탁, 브라운야드, 플루크 등
    29CM 교집합 하이버        7개   나이키, 노스페이스, 파타고니아, 폴로랄프로렌 등
    코오롱몰 교집합 하이버      0개
    셋 다                    0개

29CM 가 허브다. 코오롱몰과 하이버는 겹치는 브랜드가 하나도 없다. 코오롱몰은
국내 브랜드와 코오롱 자사(24/7 시리즈, 헨리코튼, 플루크)이고, 하이버의 브랜드
상품은 해외 스포츠와 명품(나이키, 파타고니아)이라 모집단이 갈린다. 하이버는
브랜드가 42% 에만 붙어서 애초에 11개뿐이다.

그래서 브랜드로는 "29CM 와 코오롱몰" 또는 "29CM 와 하이버" 두 채널까지만
된다. "셋이 같은 방향" 은 성립하지 않는다.

### 속성 축은 된다

    채널        속성 붙은 상품        속성 종류
    29CM        471 / 907  (52%)      62
    코오롱몰      118 / 251  (47%)      42
    하이버         36 /  50  (72%)      25

    29CM 교집합 코오롱몰     39개
    29CM 교집합 하이버       25개
    코오롱몰 교집합 하이버     22개
    셋 다                   22개

셋 다 겹치는 22개는 가디건, 기모, 긴팔, 니트, 라운드넥, 레이어드, 맨투맨,
반팔, 빈티지, 셔츠, 오버사이즈, 와이드, 울, 카라, 캐시미어, 코튼, 터틀넥,
티셔츠, 풀오버, 하프집업, 헨리넥, 후드티다.

`data/attributes.yml` 을 **한 줄도 고치지 않고** 이 수치가 나왔다. 세
사이트가 같은 한국 패션 어휘를 쓰기 때문이다. 하이버가 29CM 보다 적중률이
높은 것은 상품명이 장황해서다(`[1+1+1 할인][당일출고] 순면 기본 무지 이너
반팔 레이어드 라운드 u넥 흰색 흰티` 처럼 속성이 여러 개 들어 있다).

### 결론

**교차 확인의 축은 브랜드가 아니라 속성이다.** 브랜드 겹침은 29CM 를 끼고
두 채널까지만 쓰고, 세 채널 확인은 속성으로 한다. 이 구분을 안 하고 합쳐서
세면 "채널 셋이 확인했다" 가 사실과 다르게 된다.

하루치 측정이므로 날이 쌓이면 달라질 수 있다. 상품이 돌아가며 들어오기
때문에 브랜드 교집합은 커질 쪽이다. 그래도 모집단이 갈린 구조 자체는
바뀌지 않는다.


## 5. 분석에 넣을 때 할 일

지금은 쌓기만 한다. 순위는 소급 조회가 안 되므로 쌓는 것만 늦출 수 없고,
분석에 넣는 것은 늦춰도 과거 자료에 다시 돌릴 수 있다. 넣는 것은 눈에
보이는 선택이어야 한다.

넣으려면 이 순서다.

1. **상품명으로 유형을 뽑는다.** 코오롱몰과 하이버에 의류 카테고리가 없다.
   속성 사전은 이미 47% 와 72% 가 붙으므로(4절) 사전을 고칠 일은 적다.
   `TYPE_RULES` 쪽 적중률은 따로 재야 한다.
2. **브랜드 표기를 맞춘다.** 같은 브랜드가 채널마다 다르게 적힌다. 하이버는
   "폴로 랄프 로렌", 상품명은 "폴로랄프로렌" 이다. 띄어쓰기만 지우면 되는
   것도 있고 영문과 한글이 섞인 것도 있다. 맞추지 않으면 브랜드 겹침이
   실제보다 작게 나온다.
3. **교란 요인을 분리한다.** 코오롱몰 순위의 절반이 자사 브랜드다.
   `supplier_own` 으로 나눠서 자사와 비자사를 따로 세어야 한다. 합쳐서
   세면 코오롱 자사 밀어주기가 "유행" 으로 읽힌다.
4. **독립 창이 쌓일 때까지 기다린다.** 기준 구간과 감지 구간과 확인 구간이
   필요하다. 수집 시작이 2026-11-05 이므로 첫 창은 그보다 뒤다.

세 번째가 제일 중요하다. 채널을 늘린 목적이 "여러 채널이 같은 방향" 인데,
코오롱몰의 자사 비중을 안 걸러내면 그 방향이 브랜드 마케팅일 수 있다.


## 6. robots 근거

| 사이트 | 우리 수집기에 적용되는 규칙 | 성격 |
|---|---|---|
| 29CM | `Allow: /` | 명시적 허용 |
| 코오롱몰 | **그룹 자체가 없다** | 규칙의 부재 |
| 하이버 | `/products/*`, `/api/` 등을 막는다. `/ranking` 은 열려 있다 | 명시적 허용 |

코오롱몰에는 `User-agent: *` 그룹이 아예 없다. RFC 9309 는 내 수집기에 맞는
그룹이 하나도 없으면 제한 규칙이 없는 것으로 읽는다. **다만 이것은 명시적
허락이 아니라 규칙의 부재다.** 29CM 의 `Allow: /` 와 성격이 다르므로 보고서
와 논문에 쓸 때 구분해서 적는다.

명시된 봇들에게 막아 둔 경로는 우리에게 규칙이 없어도 쓰지 않는다. 코오롱몰
의 `/api/rest` 와 `/graphql`, 하이버의 `/products/*` 와 `/api/` 가 그렇다.
둘 다 순위 페이지가 서버 렌더링이라 그것만으로 충분하다. 사이트맵에 올라와
있는 경로만 쓴다는 원칙도 유지한다.

robots.txt 는 바뀌는 파일이다. 지그재그가 두 달 만에 바뀌었다. 한 번 확인
하고 끝내면 안 되고 수집기를 새로 붙일 때마다 다시 받는다.


## 7. 코드 위치

    src/trend_pipeline/collectors/kolon_rank.py   코오롱몰
    src/trend_pipeline/collectors/hiver_rank.py   하이버
    src/trend_pipeline/collectors/cm29_rank.py    29CM
    scripts/collect_daily.py                      셋을 따로 받고 따로 저장한다
    tests/test_commerce_channels.py               틀리면 조용히 틀릴 자리 33개

`collect_daily.py` 는 한 사이트가 죽어도 나머지를 계속 받는다. 전부 모은
뒤 한 번에 저장하면 뒤쪽이 죽을 때 앞쪽의 성공까지 끌려 내려가고, 순위는
소급 조회가 안 되므로 그렇게 날린 자료는 영영 못 되찾는다.

종료 코드는 분석이 의존하는 사이트(29CM)만 본다. 코오롱몰이나 하이버가
죽어도 0 으로 끝내서 `collect_and_push.sh` 가 29CM 스냅샷을 커밋하는 것을
막지 않는다. 실패는 로그에 눈에 띄게 적는다. 수동으로 돌릴 때 전부 성공해야
한다면 `--strict` 를 쓴다.
