데이터베이스 스키마

모든 채널의 수집 결과가 이 한 테이블로 들어옴. 채널마다 응답 형식이 다르지만 저장 형태를 통일해야 이후 단계가 채널을 구분하지 않고 동작함.

sqlite3 data/signals.sqlite ".schema signal_raw"

CREATE TABLE signal_raw (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    observed_at  TEXT    NOT NULL,              -- 지표가 가리키는 시점
    collected_at TEXT    NOT NULL,              -- 실제로 가져온 시점 (ISO8601 UTC)
    channel      TEXT    NOT NULL,              -- commerce_rank / naver_datalab / ...
    keyword_raw  TEXT    NOT NULL,              -- 수집 당시 원문 표현 (정규화 전)
    entity       TEXT    NOT NULL DEFAULT '',   -- 하위 차원: 상품ID, 'f_20', 카테고리
    metric_type  TEXT    NOT NULL,              -- rank / search_index / click_index ...
    metric_value REAL    NOT NULL,
    metadata     TEXT    NOT NULL DEFAULT '{}', -- JSON: 브랜드, URL, 카테고리
    run_id       TEXT,                          -- 같은 수집 실행을 묶는 키
    UNIQUE (channel, keyword_raw, entity, metric_type, observed_at)
);
CREATE INDEX idx_raw_observed ON signal_raw (observed_at);
CREATE INDEX idx_raw_channel  ON signal_raw (channel, observed_at);
CREATE INDEX idx_raw_keyword  ON signal_raw (keyword_raw, observed_at);

시점 컬럼을 두 개로 나눈 이유는 소급 조회 API 가 오늘 호출해도 지표는 과거를 가리키기 때문임. 하나로 합치면 모든 행이 오늘 관측으로 보여 판단 기준일 필터가 아예 성립하지 않음. UNIQUE 제약은 같은 시점의 중복 적재를 막아 재시도를 안전하게 만듦.

사건 1. 수집 대상을 바꿔야 했던 일

연계 산업체가 무신사라 무신사의 인기 순위를 수집하려 했음. 그런데 수집 정책이 허용 목록 방식이라 몇몇 검색 엔진과 지정된 수집기만 접근이 가능했고, 직접 만든 수집기는 어느 항목에도 해당하지 않았음. 정책을 어기고 모은 자료는 연구 산출물로 쓸 수 없음.

29CM 는 무신사 계열 서비스임. 본 연구의 핵심 검증 축이 "서로 독립적인 채널에서도 같은 변화가 나타나는가"인데, 계열사를 독립된 두 채널로 세면 교차검증이 헛돌게 됨. 따라서 둘을 같은 커머스 채널로 묶고, 독립 채널은 검색과 쇼핑 쪽에서 확보하기로 함.

판단 근거는 확인일과 함께 문서로 남김. 대체 결정 자체가 연구 산출물의 일부이기 때문임. 수집 허가가 확보되면 무신사 모듈을 추가할 예정임.

가설을 전제로 쓰지 않고 자료로 확인한 사례

연구계획서에 "유행은 해외에서 먼저 생겨 한국으로 들어온다"는 가정이 있었음. 이를 전제로 깔면 해외 신호를 선행 지표로 그냥 쓰게 되므로, 전제로 쓰지 않고 실제로 측정했음. 해외 시계열을 하루씩 밀어 보면서 국내와 가장 잘 맞는 지점을 찾는 방식이며, 상관계수는 값의 크기와 무관하므로 지역마다 정규화 기준이 달라도 시점 비교가 성립함.

해석그럼에도 가설을 반박하지 않은 이유

두 품목 모두 계절 상품임. 한국이 미국보다 먼저 추워지면 그 시점 차이가 선행으로 보일 수 있음. 따라서 이 수치만으로 가정이 틀렸다고 결론 내리지 않고, 계절 요인을 통제한 뒤 다시 확인하기로 함. 상관이 낮거나 탐색 범위 경계에 걸린 결과는 근거로 쓸 수 없도록 따로 표시함.

반대로 나온 결과도 한계와 함께 그대로 기록했음. 가정에 맞는 결과만 남기면 그 순간 검증이 아니라 확인 작업이 되기 때문임.

검증 파트의 결과를 코드와 대조하다가, 표에 적힌 판정이 코드의 단순 기준에서 나온 것인지 모델이 판단한 것인지 구분되지 않는다는 점을 발견했음. 양쪽이 같은 용어로 답하기 때문임. 모델의 기여를 재는 것이 본 과제의 핵심 질문인데 현재 구조로는 그것을 잴 수가 없음.
