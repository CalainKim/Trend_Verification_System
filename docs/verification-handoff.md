# 검증 파트 인수인계

담당: 이응도 (리즈닝 모델 기반 검증과 판정)
작성: 김도은 (수집, 정제, 특징 추출)

이 문서는 수집 파트가 무엇을 넘기는지, 검증 파트가 무엇을 만들어야 하는지를 적는다.


## 1. 역할 경계

수집 파트가 하는 것
  데이터 수집, 정제, 동의어 클러스터링, 특징 추출, 케이스 번들 생성
  T_cut 이전 데이터만 담기도록 보장

검증 파트가 하는 것
  번들을 입력으로 받아 확정 / 보류 / 기각을 판정
  판정에 이르는 근거와 반증 시도 과정을 남김

수집 파트는 판정 로직을 만들지 않는다. 검증 파트는 데이터를 직접 수집하지 않는다.
경계를 지켜야 "탐지와 검증의 분리"라는 설계 원칙이 실제로 성립한다.


## 2. 지금 받을 수 있는 것

    cases/case_pilot_rugby/
      meta.json            케이스 메타 (정답 라벨 없음)
      naver_datalab.csv    검색어 트렌드, 3,285행
      naver_shopping.csv   쇼핑 클릭 추이 + 성별과 연령 분해, 7,948행

형식 합의를 위한 파일럿이다. 실제 연구 케이스는 선정 기준을 합의한 뒤에 만든다.

CSV 컬럼

    observed_at    지표가 가리키는 시점
    channel        naver_datalab / naver_shopping / commerce_rank
    keyword_raw    키워드 또는 상품명
    entity         하위 구분. 빈 값이면 전체
                     gender=f / gender=m        성별
                     age=10 ~ age=60            연령
                     29cm:<상품번호>@<랭킹코드>   커머스 상품
    metric_type    search_index / click_index / rank / review_count / heart_count
    metric_value   값
    metadata       JSON. 정규화 여부, 조회 조건 등

meta.json 에는 label 과 T_peak 이 없다. 일부러 뺀 것이다. 정답을 보고 끼워맞추는
것을 막기 위해서이고, 정답은 수집 파트만 trend_case 테이블에 보관한다.


## 2-1. 지속성 케이스 (2026-10-29 추가)

역추적 케이스가 1건에서 멈춰 있었다. T_peak 을 사람이 정해야 해서다(T0).
기준 합의를 기다리는 동안 채점을 시작할 수 없어서, 정답이 자료에서 나오는
케이스를 따로 만들었다.

    benchmark/cases/<case_id>.json    문제지 139건
    benchmark/labels.digest.txt       정답 봉인 해시
    benchmark/labels.sealed.json      정답 (저장소에 없다. 수집 파트만 가진다)

### 묻는 것이 다르다

    역추적 케이스     이 후보는 real 인가 noise 인가
    지속성 케이스     이 순위 상승이 이후 N일 동안 절반 이상 유지되겠는가

원인을 묻지 않는 이유가 있다. 광고 집행과 노출 알고리즘은 쇼핑몰 안에만
있어 외부에서 관측할 수 없다. 원인은 영영 모르지만 수명은 매일 찍으면
보인다. 광고로 올린 순위는 광고가 끝나면 떨어지고 그 떨어짐은 밖에서도
보이기 때문이다.

그래서 정답을 사람이 정하지 않는다. 관측 구간에서 순위가 10계단 이상 오른
상품을 찾고, 확인 구간에서 그 상승폭의 절반이 남았는지를 자료가 답한다.
케이스가 자동으로 쌓이고 수집이 이어지는 만큼 늘어난다.

### 번들은 지금 파이프라인에 그대로 들어간다

키 이름을 src/trend_poc/review.py 의 build_payload 화이트리스트에 맞췄다.
candidate, claim, simulated_cutoff, evidence, features, limitations,
historical_available_at, experiment_type 이 들어 있다. 139건 전부
build_payload 를 통과하는 것을 확인했다.

evidence 의 id 는 여섯 개다. 모델 인용은 이 중에서만 나와야 한다.

    rank_change      순위 변화
    review_change    리뷰 변화 (구매를 거쳐야 쌓이므로 조작 여지가 적다)
    heart_change     좋아요 변화 (구매 없이도 는다)
    sale_change      할인율 변화 (늘었다면 순위 상승의 대체 설명이 된다)
    item_flags       신상품, 품절
    brand_context    같은 창에서 같은 브랜드 상품 몇 개가 함께 올랐나

sale_change 와 item_flags 는 T3 반증 축의 "특정 브랜드의 일회성 캠페인 시점과
겹치나" 를 실제로 확인할 수 있게 넣은 것이다. 이전 번들에는 없어서 그 항목을
채울 수 없었다.

limitations 를 함께 싣는다. 모델이 이것을 넘어선 주장을 하면 안 된다.

### 정답 누출은 구조로 막았다

특징을 만드는 함수와 정답을 만드는 함수가 받는 자료가 다르다. rise_events 는
기준과 관측 구간만 받고 label_events 는 확인 구간만 받는다. 한 함수가 양쪽을
보면 특징이 정답을 엿보는데 오류는 나지 않아 발견하기 어렵다.

139건을 다시 검사해 정답 값과 T_cut 이후 날짜가 한 건도 섞이지 않은 것을
확인했다.


## 2-2. 채점 방식

    python scripts/score_verdicts.py --baselines
    python scripts/score_verdicts.py --verdicts <판정 경로> --out benchmark/scorecard.md

판정 파일은 세 형태를 받는다.

    1. 디렉터리 안의 <case_id>.json     {"verdict": "WATCH"}
    2. 지금 쓰는 result.json 형식        review.verdict 또는 selection.status
    3. 하나의 매핑 파일                  {"<case_id>": "WATCH", ...}

### 판정 어휘 변환

저장소에 어휘가 세 가지 돌아다닌다. 어느 쪽으로 보내도 받는다.

    WATCH          confirm   ->  지속 예측
    NOT_SUPPORTED  reject    ->  소멸 예측
    HOLD           hold      ->  기권

모르는 값은 조용히 버리지 않고 오류를 낸다. 버리면 채점이 소리 없이 틀어진다.

### 폴더를 넘길 때 주의할 것

케이스마다 하위 폴더를 만들고 그 안에 review.json 을 쓰는 구조라면, 폴더를
그대로 넘기면 안 된다. 파일 이름이 모두 review.json 이라 case_id 가 'review'
하나로 잡히고, 정답과 한 건도 겹치지 않아 전부 기권으로 집계된다.

세 가지 중 하나로 해결한다.

    1. 파일 안에 "case_id" 를 넣는다           <- 권장
    2. 파일 이름을 <case_id>.json 으로 쓴다
    3. {case_id: verdict} 매핑 파일 하나를 넘긴다

전부 기권으로 나왔다면 성적표 아래 주석을 먼저 본다. 정답에 없는 case_id 가
몇 건이고 무엇인지 적혀 나온다. 모델이 기권한 것인지 키가 안 맞은 것인지가
거기서 갈린다.

### 기저율을 반드시 함께 본다

전체 139건의 기저율이 59.7% 다. 다수 쪽이 소멸이므로, 아무 생각 없이 전부
"소멸" 이라고 찍으면 59.7% 가 나온다. 정확도만 보고하면 찍은 것과 같은 점수를
성과로 읽는다.

    전부 소멸            커버리지 100%   정확도 59.7%   기저율 대비  -0.0%p
    전부 지속            커버리지 100%   정확도 40.3%   기저율 대비 -19.4%p
    무작위 (고정 시드)    커버리지 100%   정확도 51.1%   기저율 대비  -8.6%p

다수 쪽이 바뀐 적이 있다. 문제지를 고치기 전에는 지속이 다수(54.1%)여서
넘어야 할 선이 "전부 지속" 이었다. 아래 2-5 에 왜 바뀌었는지 적는다. 기저율은
문제지를 다시 만들 때마다 다시 재야 하고, 손으로 적어 둔 값을 믿으면 안 된다.

    python scripts/score_verdicts.py --benchmark benchmark --baselines

### 보류는 벌점이 아니지만 공짜도 아니다

보류를 오답으로 세면 신중한 판정이 벌을 받는다. 채점에서 빼기만 하면 쉬운
것만 골라 답한 판정이 상을 받는다. 그래서 커버리지와 정확도를 함께 내고,
기저율도 답한 부분집합에서 다시 계산한다.

정답이 지속인 것만 골라 답하면 정확도가 100% 가 나오지만, 그 부분집합의
기저율도 100% 라서 기저율을 넘지 못한 것으로 집계된다. 답한 부분의 기저율이
전체와 10%p 넘게 다르면 경고가 함께 나온다.

### 유의성 판정

정확도 신뢰구간의 아래끝이 기저율을 넘어야 넘었다고 본다. 점추정만 비교하면
표본이 작을 때 우연을 성과로 읽는다.

지금 표본으로 가려낼 수 있는 차이는 이 정도다. 기저율 59.7% 에서, 위 기준을
80% 확률로 통과하는 데 필요한 건수다.

    기저율 +20%p 탐지에  약  40건 필요   현재 139건  충분
    기저율 +15%p 탐지에  약  76건 필요   현재 139건  충분
    기저율 +10%p 탐지에  약 173건 필요   현재 139건  부족

**139건의 신뢰구간은 보이는 것보다 넓다.** 139건이 전부 2026-10-12 한 창에서
나왔다. 창이 겹치지는 않지만 같은 날 같은 쇼핑몰의 상품들이라, 그날 어떤
기획전이 돌았는지 같은 공통 요인을 함께 받는다. 신뢰구간 공식은 139건이 서로
무관하다고 가정하므로 실제보다 좁게 나온다.

수집이 쌓여 창이 둘 셋으로 늘면 그때 창 사이 비교가 가능해진다. 그때까지는
"유의해 보인다" 까지만 말해야 한다.


## 2-3. 역추적 지속성 케이스 (검색 지수)

커머스 케이스는 수집을 시작한 날부터만 만들 수 있다. 29일로는 독립 창이
하나뿐이라 통계적 주장을 할 수 없다. 검색 지수는 과거를 소급 조회할 수 있어
같은 질문을 몇 년치로 물을 수 있다.

묻는 것은 커머스와 같다. 올랐는가가 아니라 오른 것이 버티는가이다. 다른 것은
상승을 계단 수가 아니라 비율로 잰다는 점뿐이다. 지수는 요청 창 안에서
정규화된 상대값이라 차이의 절대 크기에 뜻이 없다.

### 벤치마크가 셋이다

    benchmark/              29CM 순위     확인  7일   139건   기저율 59.7% (소멸 다수)
    benchmark-index/        검색 한국     확인 28일   207건   기저율 61.8% (지속 다수)
    benchmark-index-long/   검색 3개 지역  확인 84일   352건   기저율 50.3% (소멸 다수)

번들 형식과 채점기는 셋이 같다.

    python scripts/score_verdicts.py --benchmark benchmark-index --baselines

**셋을 합쳐 하나의 점수로 내면 안 된다.** 기저율이 47% 에서 74% 까지 벌어진다.
지표의 성질과 확인 기간이 다르기 때문이고, 각자의 기저율과 비교해야 한다.

### 확인 기간을 왜 28일과 84일로 나눴나

확인 기간을 줄이면 같은 자료에 창이 더 많이 들어가 케이스가 늘지만, 묻는
질문이 약해진다. 측정한 교환비는 이렇다.

    확인기간   독립 창   키워드 74개일 때 예상 케이스
      84일       10              약  50건 (한국만)
      28일       25              약 190건

28일을 주 벤치마크로 둔 이유는 산업체가 말한 문제가 재고 확보 대응이고 그
시계가 며칠에서 몇 주이기 때문이다. 발주 판단에는 모자라므로 84일 보조
벤치마크를 함께 둔다.

84일은 한국만으로는 표본이 모자라 세 지역을 함께 쓴다. '헨리넥' 한국 검색의
상승과 'henley shirt' 미국 검색의 상승은 다른 사건이므로 각각 센다. 다만
같은 유행이 양쪽에 걸칠 수 있어 완전히 독립은 아니고, 성적표에 그 사실이
함께 나온다.

### 계절성 지표가 들어 있다

features 의 yoy_ratio 가 작년 같은 기간 대비 비율이다. 1 에 가까우면 해마다
반복되는 움직임이고, 그렇다면 계절성으로 설명된다. T3 반증 축의 "계절성으로
설명되나" 를 이 값으로 확인할 수 있다. 커머스 케이스에는 과거 자료가 없어
넣지 못한 항목이다.

작년 자료가 없으면 null 이다. 억지로 메우지 않는다. 메우면 계절성이 없다고
잘못 읽는다.

### 지금은 표본이 모자란다

키워드가 9개뿐이라 셋 다 +20%p 개선만 가려낼 수 있다. 사전
(data/attributes.yml)에 74개가 있고 전부 수집하면 주 벤치마크가 190건쯤 된다.
구글 트렌드는 연속 24회쯤에서 IP 단위로 막히고 몇 시간 뒤 풀리므로 며칠에
나눠 받아야 한다.

수집한 뒤에는 이 한 줄로 셋을 다시 만든다. 창 구성은 스크립트에 고정했다.

    ./scripts/build_all_benchmarks.sh

창 구성을 바꾸면 케이스 id 가 달라지므로 옛 문제지는 자동으로 지워진다.
남겨 두면 문제지가 정답보다 많아져서 채점할 수 없는 케이스를 돌리게 된다.


## 2-4. 지금까지 나온 성적 (2026-11-03)

수집 파트가 기존 판정기(src/trend_poc/review.py)로 139건을 돌린 결과다. 검증
파트가 만들 판정기가 넘어야 할 선이 이것이다.

    모델    답변  95건   커버리지  68.3%   정확도 77.9%   기저율 대비 +11.6%p   유의함
    규칙    답변 139건   커버리지 100.0%   정확도 58.3%   기저율 대비  -1.4%p   유의하지 않음

규칙은 전부 답하고 모델은 기권한다. 그래서 두 정확도를 나란히 놓고 읽을 수
없다. 모델이 쉬운 것만 골라 답했을 가능성을 기저율로 거른다. 답한 95건의
기저율이 66.3% 로 전체(59.7%)보다 높아 조금 쉬운 쪽을 골랐고, 채점은 그
66.3% 를 넘어야 통과로 센다.

규칙 기준선은 "순위가 많이 올랐으면 지속" 처럼 손으로 짠 임계값이다. 이것이
기저율을 넘지 못한다는 사실이 중요하다. 리즈닝 모델을 쓸 이유가 여기서 나온다.

답한 95건의 내역이다.

    정답 \ 예측      소멸    지속
    소멸              55       8
    지속              13      19

두 가지를 구분해서 읽어야 한다.

    모델이 소멸이라고 한 68건 중 55건이 맞다          81%
    모델이 지속이라고 한 27건 중 19건이 맞다          70%

    실제로 소멸한 63건 중 55건을 잡아냈다            87%
    실제로 지속한 32건 중 19건을 잡아냈다            59%

**못 버틸 것을 가려내는 쪽이 양쪽 기준에서 모두 낫다.** 재고 판단에서는 이쪽이
더 값어치가 있으니, 정확도 하나로 묶지 말고 방향별로 보고하는 편이 낫다.

성적표 원본은 benchmark/scorecard.md 에 있다.


## 2-5. 문제지를 두 번 고쳤다 (2026-11-03)

이전 성적(61건, 정확도 70.8%)과 숫자가 다른 이유다. 모델을 바꾼 것이 아니라
문제지에 있던 결함을 고쳤다. 검증 파트가 옛 숫자와 비교하면 안 된다.

### 고친 것 하나. 확인 구간이 특징으로 새고 있었다

계절성 지표(yoy_ratio)를 만들 때 날짜 창 양쪽에 여유를 두고 평균을 냈다. 그
여유가 뒤쪽으로도 뻗어서 T_cut 이후 날짜를 끌어왔다. 48개 값 중 47개가
오염됐다. 여유를 앞쪽으로만 주도록 고쳤다.

오류가 나지 않는 종류의 결함이었다. T_cut 검사는 번들에 실리는 관측치만
보는데, 이 누출은 특징값 계산 과정에서 일어나 번들에는 숫자 하나로만
남기 때문이다.

### 고친 것 둘. TOP100 밖으로 나간 날을 버리고 있었다

수집은 하루 상위 100위까지만 받는다. 101위 밖으로 밀려난 상품은 그날 목록에
없다. 이것을 "모르는 값" 으로 보고 평균에서 빼면, 하루만 7위에 떴다가 사라진
상품이 "평균 7위" 가 되어 42계단 상승으로 잡힌다. 가장 뚜렷한 소멸 사례가
정답에서 빠지기도 했다(80건 중 18건).

목록이 100위까지이므로 밖에 있었다는 것은 "101위보다 나쁘다" 는 정보다.
경계값 101 로 채워 평균에 넣는다. 번들의 rank_change 근거에 그날이 결측인지
목록 밖인지가 글로 적혀 나간다.

문제지가 61건에서 139건으로 늘어난 것도 이 수정 때문이다. 버려지던
케이스가 돌아왔다.

### 근거를 뭐라고 쓰는지가 기권율을 바꿨다

같은 자료, 같은 모델, 같은 61건에서 근거 문장의 '결측' 을 'TOP100 밖' 으로
바꾸자 커버리지가 39.3% 에서 68.9% 로 올랐다. 모델은 모르는 값 앞에서
기권한다. 자료가 실제로 무엇을 뜻하는지 적어 주는 것만으로 답을 하게 된다.

프롬프트를 설계할 때 참고할 만하다. 기권이 많으면 모델을 의심하기 전에 근거
문장이 모호한지 먼저 보는 편이 빠르다.


## 3. 데이터를 읽을 때 반드시 알아야 할 것

### 값은 절대량이 아니라 상대 지수다

네이버 두 API 는 조회 구간의 최댓값이 100 이 되도록 정규화한 값을 준다.
같은 요청 안의 값끼리만 비교가 성립한다. 케이스 A 의 80 과 케이스 B 의 80 은
전혀 다른 크기다. 케이스 간 비교가 필요하면 변화율이나 기울기처럼 스케일에
영향받지 않는 형태로 바꿔서 봐야 한다.

### 20대 남성은 교차 조건으로 받아야 한다

3차 문서에서 1차 MVP 대상이 20대 남성으로 확정됐다. 이 집단의 자료는
성별과 연령을 **한 요청에 함께 지정**해서 받는다. 두 API 모두 교차 조건을
지원하는 것을 실측 확인했다 (2026-09-27).

    검색어 트렌드   gender=m + ages=[3,4]    (5세 단위라 19-24, 25-29 두 코드)
    쇼핑인사이트    gender=m + ages=[20]     (10년 단위)

번들에서는 entity 로 구분된다.

    (빈 값)              전체
    gender=m             남성 전체        <- 주변분포
    age=20               20대 전체        <- 주변분포
    gender=m;ages=3+4    20대 남성        <- 교차셀

**주변분포 두 개로 교차셀을 복원할 수 없다.** '남성 전체'와 '20대 전체'를
겹쳐서 20대 남성이라고 해석하면 안 된다. entity 에 `;` 가 있는 행만이
교차 조건으로 받은 자료다.

연령 코드 체계가 두 API 사이에 다르다. 검색어 트렌드는 1~11(5세 단위),
쇼핑인사이트는 10~60(10년 단위)이다. 섞어 쓰면 엉뚱한 구간을 받는다.

### 좁은 세그먼트는 결측이 많다

클릭이 없는 날은 응답에서 행 자체가 빠진다. "0 클릭"과 "데이터 없음"이
구분되지 않으므로 metadata 의 `returned_days` 로 커버리지를 확인해야 한다.

키워드 물량이 적을수록 심해진다. 실측 예로 '맨투맨'을 2개월 구간에서
20대 남성으로 좁히니 62일 중 13일(21%)만 돌아왔다. 같은 조건이라도
'럭비티'를 3년 구간으로 보면 97%가 나온다.

결측이 많은 구간에서 추세를 읽으면 안 된다. 자료 부족은 보류 사유다.

### 연령 분포에는 채널 편향이 있다

여성과 남성 티셔츠 분야 모두 최다 연령대가 40 대로 나온다. 네이버쇼핑 이용자층이
그런 것이지 해당 키워드의 특성이 아니다. 무신사 이용자층과는 다르다.

    50000167 여성>티셔츠   여성 69.5 / 남성 2.2    최다 40대 (64.2)
    50000169 남성>티셔츠   남성 44.1 / 여성 15.3   최다 40대 (42.4)

"특정 연령에 국한된 현상인가"를 판단할 때 40 대 비중이 높다는 사실만으로
결론 내면 틀린다. 채널의 기저 분포 대비 얼마나 치우쳤는지를 봐야 한다.

### 쏠림은 리프트로 읽는다

수집 파트가 분야 전체의 분포를 기준선으로 함께 수집한다. 번들에서
keyword_raw 가 `category:<코드>` 인 행이 기준선이다.

    리프트 = 키워드의 그룹 점유율 / 분야 전체의 그룹 점유율

1 이면 분야 평균과 같고, 2 면 두 배로 쏠렸다는 뜻이다. 실측 예
(남성의류>티셔츠, 2026-06 ~ 08):

    반팔티   40대 1.20 / 20대 0.83   쏠림 없음. 여름 필수품
    맨투맨   20대 1.31 / 60대 0.34   약한 젊은 층 쏠림
    정장     20대 2.78 / 60대 0.14   뚜렷한 젊은 층 쏠림

기저 점유율이 2% 미만인 그룹은 분모가 작아 리프트가 폭주한다(10 대가 그렇다).
이런 행은 참고용으로만 보고 판단 근거로 쓰지 않는다.

얼마부터 "국한"으로 볼지는 정해져 있지 않다. 수집 파트는 얼마나 쏠렸는지만
계산하고, 임계값은 검증 파트가 정한다.

### T_cut 이후 데이터는 없다

번들에는 T_cut 이전 관측치만 들어 있다. 내보내기 직전에 한 번 더 검증하며,
한 건이라도 위반하면 생성 자체가 중단된다. 이후 시점 데이터를 별도로 찾아보는
것은 실험을 무효로 만든다.


## 4. 판정 결과 형식 (제안, 합의 대상)

케이스 폴더에 verdict.json 을 쓰는 방식을 제안한다. 스키마 초안은
verification/verdict.example.json 에 있다. 바꿀 부분이 있으면 말해 달라.

핵심은 판정 값 자체가 아니라 근거와 반증 시도가 남는 것이다. 이 연구의 평가
기준이 예측 정확도가 아니라 절차의 투명성과 반증 가능성이기 때문이다.


## 5. 태스크

### T0. 케이스 선정 기준 합의 (공동, 역추적 케이스에만 해당)

2026-10-29 기준. 지속성 케이스(2-1)는 이 합의를 기다리지 않고 채점을 시작할
수 있다. 정답이 자료에서 나오기 때문이다. T0 는 역추적 케이스에만 남는 숙제다.


무엇을 real 로 보고 무엇을 noise 로 볼지 조작적으로 정의한다.
기준을 먼저 고정하고 그에 맞는 사례를 찾는 순서여야 한다. 사례를 먼저 고르면
이미 결과를 아는 상태에서 기준을 만들게 되어 편향이 들어간다.

정해야 할 것
  - 무엇을 "폭발한 시점(T_peak)"으로 볼 것인가
  - 지속 기간이 얼마 이상이면 real 인가
  - 노이즈의 하위 유형 (반짝 유행 / 캠페인 효과 / 특정 집단 국한)을 어떻게 구분하나

### T1. 확정 / 보류 / 기각의 조작적 정의

세 판정을 가르는 조건을 문서로 고정한다. 특히 "보류"의 조건이 중요하다.
보류가 없으면 애매한 것을 억지로 한쪽으로 밀게 된다.

### T2. 리즈닝 모델 프롬프트 설계

번들을 입력으로 받아 근거를 수집하고 군집화하는 절차. 계획서의 목표 1 에 해당한다.
최종 확정 판단을 모델에 위임하지 않는 구조여야 한다.

### T3. 반증 절차 설계

모델이 스스로 반증을 시도하는 별도 단계. 계획서의 목표 3 이다.
확증편향 방지가 목적이므로, 근거 수집과 같은 호출에서 처리하면 안 된다.
검토할 반증 축의 예
  - 독립 채널에서도 같은 변화가 있나, 아니면 한 채널만인가
  - 특정 브랜드의 일회성 캠페인 시점과 겹치나
  - 특정 연령이나 성별에만 국한되나 (채널 기저 분포 대비)
  - 계절성으로 설명되나 (작년 같은 시기에도 올랐나)

### T4. 파일럿 케이스로 1회 판정 수행

case_pilot_rugby 로 실제 돌려보고, 판단에 필요한데 번들에 없는 정보를 알려 달라.
이게 가장 급하다. 특징 추출을 다시 설계해야 하면 지금 알아야 한다.

### T5. 판정 결과 스키마 확정

verification/verdict.example.json 을 검토하고 필요한 필드를 추가한다.

### T6. 벡터 검색 결과의 활용 방식 정의

수집 파트가 후보를 실제 수집 아이템으로 연결해 준다. 판정 결과에 이 아이템
목록을 어떤 형태로 담을지 정한다. 최종 산출물이 개념이 아니라 아이템으로
떨어져야 재고 대응에 쓸 수 있다.

### 해외 선행은 계절성과 구분해야 한다

Google Trends 로 한국과 해외의 관심도 시계열을 받아, 해외를 며칠 밀었을 때
한국과 가장 잘 겹치는지로 선행 일수를 잰다. 상관계수는 스케일에 무관하므로
지역마다 정규화 기준이 달라도 시점 비교는 성립한다.

번들에서 entity 가 `geo=KR` / `geo=US` / `geo=WORLD` 인 행이다.

    lead_days > 0    해외가 그만큼 앞섰다
    lead_days < 0    한국이 앞섰다

세 가지를 확인하고 써야 한다.

  - **상관이 낮으면 근거로 쓸 수 없다.** 어긋난 두 곡선을 억지로 맞춘 결과다.
  - **탐색 범위 끝에 걸린 값은 쓸 수 없다.** 진짜 최적이 범위 밖일 수 있다.
  - **계절 상품은 계절 차이만으로 선행이 나타난다.** 한국과 해외의 계절 검색
    시점이 다르기 때문이다. 전년 동기 대비 지표를 함께 봐야 구분된다.

실측 예 (2024-01 ~ 2026-09): 맨투맨은 한국이 미국보다 21일 앞서고(상관 0.61),
후드티는 35일 앞선다(상관 0.66). 계획서가 전제한 "유행은 해외에서 한국으로
넘어온다"와 방향이 반대다. 다만 둘 다 계절 상품이라 이 수치만으로 가설을
반박할 수는 없다. 계절성을 통제한 뒤에 다시 봐야 한다.

한국어 키워드는 해외 검색량이 구조적으로 0이라 대응 영문 단어를 함께 조회한다.
두 단어가 같은 개념을 가리킨다는 가정이 들어가므로, 대응이 어색한 키워드는
선행 판단에서 제외해야 한다.
