그림 10

문제와 대응 타임라인

모두 코드를 쓰다가 발견한 것이 아니라 결과를 눈으로 확인하다가 드러난 문제임. 그래서 화면과 터미널 출력으로 원본을 직접 확인하는 절차를 작업 과정에 넣어 두었음.

그림 11

사건 1. 수집 대상 변경 (무신사에서 29CM 로)

문제

산업체가 무신사라 무신사 랭킹을 수집하려 했으나, 수집 정책이 허용 목록 방식이라 직접 만든 수집기는 어느 항목에도 해당하지 않아 전면 차단 대상이었음. 정책을 어기고 모은 자료는 연구 산출물로 쓸 수 없음.

사이트일반 수집기 규칙판정
무신사User-agent: * Disallow: / (허용 목록 방식)불가
W컨셉허용 목록 전용, 일반 수집기 명시 없음불가
29CMAllow: / (마이페이지와 주문 등만 차단)가능
지그재그Allow: / (생성형 수집기만 차단)가능
에이블리정책 파일 응답 없음약관 확인 필요

대응  29CM 를 대체 소스로 채택하되 독립 채널로 세지 않음

29CM 는 무신사 계열 서비스임. 본 연구의 핵심 검증 축이 "서로 독립적인 채널에서도 같은 변화가 나타나는가"이므로, 계열사를 두 채널로 세면 교차검증이 성립하지 않음. 따라서 둘을 같은 커머스 채널로 묶고, 독립 채널은 검색과 쇼핑 쪽에서 확보함. 수집 허가가 확보되면 무신사 모듈을 추가할 예정임.

판단 근거는 저장소 docs/robots-compliance.md 에 확인일과 함께 기록해 두었음. 대체 결정 자체가 연구 산출물의 일부임.

그림 12

사건 2. 하루 두 번 수집했더니 순위가 섞임

문제

수집 누락에 대비해 하루 두 번 수집하도록 했는데, 관측 시점을 날짜까지만 기록한 탓에 두 실행이 같은 키로 충돌했음. 중복을 막는 제약이 1차 실행값을 지키는 사이, 그동안 랭킹에 새로 진입한 상품만 통과해서 한 날짜 안에 서로 다른 시점의 순위가 섞이고 같은 순위가 두 번 나타났음. 부분 실패한 실행이 그날 자료를 영구히 오염시키는 경로이기도 했음.

고치기 전

observed_at = 2026-09-08

10시 실행  1위 A상품   저장됨
          2위 B상품   저장됨
22시 실행  1위 C상품   기각 (키 충돌)
          2위 A상품   기각 (키 충돌)
          3위 D상품   저장됨  ← 신규 진입만 통과

결과: 한 날짜에 10시와 22시 순위가 혼재
      같은 순위가 두 번 나타남
→

고친 뒤

observed_at = 2026-09-08T10:00:31
             2026-09-08T22:06:12

10시 실행  1위 A상품   저장됨
          2위 B상품   저장됨
22시 실행  1위 C상품   저장됨
          2위 A상품   저장됨
          3위 D상품   저장됨

결과: 실행마다 독립 스냅샷
      하루 두 번이 중복이 아니라 이중화가 됨

함께 드러난 문제  유니섹스 상품의 순위 유실

같은 상품이 여성 랭킹과 남성 랭킹에 동시에 오르는 경우, 두 행이 같은 키로 충돌해 한쪽이 사라졌음. 순위를 기록하는 행에만 랭킹 목록 코드를 포함시켜 두 행이 각각 남도록 고쳤음. 기존 스냅샷도 같은 형식으로 정정하고 회귀 테스트 3건을 추가함.

일 단위로 분석할 때는 그날의 스냅샷 하나만 고르도록 별도 함수를 두었음. 서로 다른 실행을 섞으면 안 되기 때문임.

그림 13

사건 3. 클라우드 자동 수집이 38회 전부 실패

문제

일별 자동 수집을 클라우드 자동화로 구성했으나, 수집 대상이 클라우드 사업자의 IP 대역에서 오는 요청을 차단했음. 실행은 매일 돌았지만 자료는 한 건도 쌓이지 않았고 실패 알림만 누적됐음. 커머스 자료는 소급 수집이 불가능하므로 그 기간은 영구 결측이 됐음.

대응  예약 실행을 걷어내고 로컬 실행으로 전환

항목처리
예약 실행제거함. 수동 실행만 남겨 네트워크 조건이 바뀌었는지 확인하는 용도로 둠
실제 수집개인 장비에서 하루 두 번 실행하도록 전환함 (2026-09-29 부터)
결측 처리숨기지 않고 화면에 그대로 표시함
판단 기록워크플로 파일 상단에 제거 사유를 남겨 다시 켜지 않도록 함

이 결정으로 수집 안정성은 개인 장비의 전원과 네트워크 상태에 묶이게 됐음. 그 대가로 자료가 실제로 쌓이게 됐으며, 남은 취약점은 사건 6에서 다시 다룸.

그림 14

사건 4. 비율 지표의 분자와 분모 기간이 어긋남

문제

특정 키워드가 어느 연령대에 쏠려 있는지 보려면 분야 전체의 연령 분포를 기준선으로 두고 키워드의 분포를 나눠야 함. 그런데 사례를 만들면서 기준선에 2021년부터 2024년까지의 자료가 추가됐고, 키워드 쪽은 2026년 6월부터 8월 자료만 있었음. 서로 다른 기간을 비교하게 되면서 값이 뒤집혔음.

기간이 어긋났을 때

기준선   2021-01 ~ 2024-12 평균
관측치   2026-06 ~ 2026-08 평균

반팔티 20대 리프트 = 0.27

해석: "반팔티는 20대가 거의 안 찾는다"
      계절 필수품인데 특정 연령에
      집중된 품목으로 나옴
→

공통 구간으로 맞춘 뒤

기준선   2026-06 ~ 2026-08 평균
관측치   2026-06 ~ 2026-08 평균

반팔티 20대 리프트 = 0.83

해석: "반팔티는 연령대별로 고르게
      찾는 품목이다"
      상식과 맞는 결과

대응

기준선과 관측치가 모두 존재하는 구간으로 자동 제한하도록 고치고 회귀 테스트 2건을 추가함. 비율 지표는 분자와 분모가 같은 조건이어야 한다는 원칙을 코드에 강제함.

이 결함은 코드를 읽어서가 아니라 미팅용 시연을 만들어 직접 돌려보다 값이 이전과 달라진 것을 발견해 드러났음. 이후로는 화면과 터미널로 결과를 눈으로 확인하는 절차를 작업에 포함했음.

그림 15

사건 5. 같은 입력에 실행마다 다른 답이 나옴

문제

후보 키워드와 상품명을 연결할 때, 상품명을 단어 단위로 쪼갠 뒤 다시 이어 붙여 포함 여부를 확인했음. 그런데 쪼갠 결과를 집합에 담아 이어 붙이면 순서가 보장되지 않음. 파이썬이 문자열 해시를 실행할 때마다 다르게 잡기 때문임. 그 결과 같은 자료로 같은 코드를 돌려도 답이 달라졌음.

$ python -c "print(lexical_match('후드티', 'C로고 레귤러핏 후드 티셔츠 Oxford Grey'))"
True
$ python -c "print(lexical_match('후드티', 'C로고 레귤러핏 후드 티셔츠 Oxford Grey'))"
False      ← 같은 명령, 같은 자료, 다른 답
$ python -c "print(lexical_match('후드티', 'C로고 레귤러핏 후드 티셔츠 Oxford Grey'))"
True

대응  순서를 보존하도록 고치고 회귀 테스트로 고정

고치기 전고친 뒤
"".join(토큰집합)
집합에 담는 순간 순서를 잃음		 구분자만 제거하고 원래 순서 유지
같은 입력이면 항상 같은 문자열
검증 수단 없음같은 입력을 20회 반복해 결과가 하나로 모이는지 확인하는 테스트 추가

본 연구의 평가 기준이 결과의 정확도가 아니라 절차의 투명성과 재현 가능성이므로, 이 결함은 성능 문제가 아니라 연구 자체를 무효로 만드는 종류였음. 지도교수나 팀원이 같은 코드로 다른 결과를 얻으면 어떤 주장도 검증할 수 없기 때문임.

그림 16

가설을 전제로 쓰지 않고 자료로 확인한 사례

연구계획서에 "유행은 해외에서 먼저 생겨 한국으로 들어온다"는 가정이 있었음. 이를 전제로 깔면 해외 신호를 선행 지표로 그냥 쓰게 되므로, 전제로 쓰지 않고 실제로 측정했음. 해외 시계열을 하루씩 밀어 보면서 국내와 가장 잘 맞는 지점을 찾는 방식이며, 상관계수는 값의 크기와 무관하므로 지역별 정규화 기준이 달라도 시점 비교가 성립함.

그럼에도 가설을 반박하지 않은 이유

두 품목 모두 계절 상품임. 한국이 미국보다 먼저 추워지면 그 시점 차이가 선행으로 보일 수 있음. 따라서 이 수치만으로 가정이 틀렸다고 결론 내리지 않고, 계절 요인을 통제한 뒤 다시 확인하기로 함. 상관이 낮거나 탐색 범위 경계에 걸린 결과는 근거로 쓸 수 없도록 따로 표시함.

반대로 나온 결과도 한계와 함께 그대로 기록했음. 가정에 맞는 결과만 남기면 그 순간 검증이 아니라 확인 작업이 되기 때문임.

그림 17

현재 위치와 남은 경로

현재 막혀 있는 것은 코드가 아니라 합의임. 수집, 정제, 특징 추출, 산출물 생성, 모델 판정, 결과 화면이 모두 동작하나 검증할 사례가 없어 실험을 수행하지 못하고 있음.

그림 18

모델이 실제로 기여하는지 재는 방법

발견한 문제

검증 파트의 결과를 코드와 대조하다가, 표에 적힌 판정이 코드의 단순 기준에서 나온 것인지 모델이 판단한 것인지 구분되지 않는다는 점을 발견했음. 양쪽이 같은 용어로 답하기 때문임. 모델의 기여를 재는 것이 본 과제의 핵심 질문인데, 현재 구조로는 그것을 잴 수가 없음.

지금 구조

        같은 사례
           │
     ┌─────┴─────┐
  단순 기준     모델
  (20% 증가)   (근거 작성)
     │           │
     └─────┬─────┘
        한 칸에 합쳐 표기

→ 어느 쪽 답인지 구분 불가
→

바꿀 구조

        같은 사례
           │
   ┌───────┼───────┐
단순 기준  모델 A  모델 B
(20% 증가) (상용)  (공개)
   │       │       │
   └───────┼───────┘
     각각 따로 표기

→ 갈리는 건수 = 모델의 기여도

비교 설계

비교 대상내용확인하려는 것
단순 기준쇼핑 지수가 일정 비율 이상 늘면 후보로 봄모델 없이 어디까지 맞히는가
상용 모델Claude API 로 같은 근거를 주고 판단과 이유를 받음단순 기준 대비 몇 건이 달라지는가
공개 모델직접 실행하는 추론 모델로 같은 근거를 줌버전 고정이 가능한 환경에서 같은 결과가 나오는가

세 대상이 모두 같은 답을 내더라도 그것 역시 보고할 결과임. 모델이 기여하지 않았다는 사실을 수치로 보이는 것도 검증의 일부이기 때문임. 공개 모델을 함께 보는 이유는 상용 API 가 갱신되면 같은 입력에 다른 답이 나올 수 있는 반면 공개 모델은 버전을 고정할 수 있어, 재현 가능성이 평가 기준인 본 과제에 더 맞기 때문임.
